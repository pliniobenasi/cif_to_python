# Event semantics

## Goal

The generated runtime must make a clear distinction between:

```text
external events
automatic events
temporal events
internal transitions
```

This is necessary because CIF is event-driven, while the target simulator also supports step-driven execution.

## Runtime policy

| Event kind | Example | Runtime policy |
|---|---|---|
| plain `event` | `event input_coffee;` | external by default |
| `controllable` | `controllable event start;` | external by default |
| `uncontrollable` | `uncontrollable event day;` | automatic candidate during `step(...)` |
| conventional temporal event | `tick`, `time_step`, `hour`, `day`, `daily_update` | automatic temporal candidate during `step(...)` |
| edge without event | `edge when ... do ...` | internal automatic transition |

## `fire(event)`

`fire(event)` is the explicit event-driven API.

It is used when an event is supplied from outside the module.

Typical case:

```text
CoffeeMachine.fire("input_coffee")
```


## Strict event-trace execution

When an event sequence is supplied explicitly through an event CSV trace, each requested event is mandatory. If no edge with that event is enabled in the current CIF state, the generated runtime raises an error instead of treating the event as a silent no-op.

This mirrors ESCET trace-input mode: a trace item is valid only when the requested event can actually be consumed by the current state. The `ship-counter-optimized` negative scenario is used as a regression example: after `count = 5`, another `ship_enters` event is rejected because the guard `count < 5` is false.

## `step(input_data)`

`step(input_data)` is the step-driven API.

It is used by the modular engine to advance simulation time and to update modules using bound inputs.

During `step(...)`, the runtime may evaluate:

```text
internal eventless transitions
automatic temporal events
uncontrollable events according to the current policy
```

## Limits

The current implementation does not reproduce the full ESCET/CIF supervisory-control semantics.

In particular:

```text
complete global event synchronization is not implemented
controllable/uncontrollable are mapped to a runtime trigger policy
urgent semantics are not implemented
priority semantics are not implemented
```

This is documented as a limitation and future work.

## Reverse-engineering result from ESCET Java code

A detailed comparison with the Java `cifcode` generated by ESCET for
`Grid_semplified.cif` showed that the guards and updates of the translated
Python modules were mostly faithful, but the runtime scheduling policy was too
weak.

In particular, the generated Java code for `Biomass.day` resets `cd` but does
**not** reset the local continuous clock `c`. This means that after a `day`
transition, another automatic `hour` transition may become enabled almost
immediately.

To match this behavior more closely, the generated Python runtime no longer
fires at most one automatic edge per logical step. Instead, after advancing the
derivatives once for the step, it repeatedly fires automatic/internal edges
until no more are enabled.

This fix is general and belongs to the runtime core rather than to the
`Grid_semplified` case study only.
