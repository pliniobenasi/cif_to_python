# Generated runtime vs PyCrop-hosted behavior comparison

This note documents the dedicated comparison workflow between:

- the **generic runtime** generated by the CIF -> modular Python pipeline;
- the **same generated modules hosted in the original PyCrop `SimulationEngine`** through the adapter bridge.

The comparison is performed on exported **history CSV traces**, not on source code.

## Why a dedicated comparison is useful

The PyCrop adapter demonstrates that generated modules can be hosted inside an external modular simulator. However, executable compatibility does not automatically imply full behavioral identity.

For this reason, the package includes a dedicated script:

```text
validation/compare_with_pycrop_behavior.py
```

The script:

1. runs the generated package in the generic runtime and exports its history to CSV;
2. runs the same generated package inside PyCrop and exports the hosted history to CSV;
3. compares the two traces sample-by-sample on the selected variables;
4. writes a Markdown/CSV/JSON report in an output directory.

## CoffeeMachine example

```bash
python3 validation/compare_with_pycrop_behavior.py \
  --pycrop-root ._pycrop/PyCrop_restrict \
  --cif examples/coffee_machine.cif \
  --events-csv examples/coffee_machine_events.csv \
  --seconds 6 \
  --history-vars CoffeeMachine_0_location 
```

Expected outcome:

- `status: pass`
- `mismatched cells: 0`

Reason: after the event-target dispatch fix, the PyCrop-hosted history matches the generic runtime on the observed location trace.


## ShipCounter guarded counter example

```bash
python3 validation/compare_with_pycrop_behavior.py \
  --pycrop-root ._pycrop/PyCrop_restrict \
  --cif examples/ship-counter-optimized.cif \
  --events-csv examples/ship-counter-optimized_events.csv \
  --seconds 10 \
  --history-vars ShipCounter_0_count ShipCounter_0_location \
  --var-map ShipCounter_0_count=ShipCounter_0_count \
  --var-map ShipCounter_0_location=ShipCounter_0_location 
```

Expected outcome:

- `status: pass`
- `mismatched cells: 0`

This example is useful because it validates guarded self-loops and discrete updates along an executable event trace. Disabled guarded events are intentionally not treated as no-ops: a separate negative scenario asks for one extra `ship_enters` after `count = 5`, and both ESCET and the generated runtime reject that trace.

## Grid_semplified example (48h)

```bash
python3 validation/compare_with_pycrop_behavior.py \
  --pycrop-root ._pycrop/PyCrop_restrict \
  --cif examples/Grid_semplified.cif \
  --input-csv examples/grid_weather_input_48h_repeat.csv \
  --hours 48 \
  --limit 5 \
  --history-vars Greenhouse_Rad Nodes_0_N LAI_0_lai Biomass_0_w 
```

Expected outcome on the current bridge:

- `status: fail`
- mismatches concentrated on `LAI_0_lai` and `Biomass_0_w`
- `Greenhouse_Rad` and `Nodes_0_N` aligned on the observed samples

This is the expected result with the current host engine. It reflects the single-pass update policy of the original PyCrop `SimulationEngine`, not a failure of the adapter to execute the model.

## Grid_semplified example (24h)

```bash
python3 validation/compare_with_pycrop_behavior.py \
  --pycrop-root ._pycrop/PyCrop_restrict \
  --cif examples/Grid_semplified.cif \
  --input-csv examples/grid_weather_input.csv \
  --hours 24 \
  --limit 5 \
  --history-vars Greenhouse_Rad Nodes_0_N LAI_0_lai Biomass_0_w 
```

Expected outcome on the current bridge:

- `status: fail`
- a single mismatch at the first day boundary on `LAI_0_lai`

This shorter run is still useful because it makes the first visible divergence easy to inspect.

## Outputs produced

For each comparison run, the script writes:

- `generated_trace.csv`
- `pycrop_trace.csv`
- `pycrop_summary.json`
- `generated_vs_pycrop_behavior.csv`
- `generated_vs_pycrop_behavior.md`
- `generated_vs_pycrop_behavior.json`

## Interpretation

The comparison should be read as follows:

- **pass** means the PyCrop-hosted bridge reproduces the observed generic-runtime behavior on the selected variables;
- **fail** means the two hosts expose different behavior traces on the selected variables.

For `coffee_machine`, `traffic_light_temporal`, and `ship-counter-optimized`, the comparison is currently a full behavioral match on the selected observables.
For `Grid_semplified`, the comparison is intentionally informative: it documents the current semantic gap between the generic runtime and the PyCrop host on day-boundary-sensitive chains such as `Nodes -> LAI -> Biomass`.
