# Generic engine vs PyCrop hosting benchmarks

This note summarizes the lightweight benchmark used to compare the execution of one generated package in:

- the **generic runtime** produced by the CIF -> modular Python pipeline;
- the **PyCrop-hosted adapter bridge**.

## Scope and limitations

The benchmark is intentionally simple and reproducible from the command line. It measures **end-to-end CLI execution time**, not only the pure inner stepping loop. Therefore the numbers include:

- Python process startup;
- package loading;
- engine construction;
- scenario execution;
- normal CLI teardown.

This makes the benchmark useful as a project-level comparison of the two hosting modes, but it should not be over-interpreted as a micro-benchmark of the internal simulation step. Semantic correctness is validated separately by the behavior-comparison scripts.

## Script

The benchmark is now scenario-based. It no longer runs a hardcoded suite of CoffeeMachine and Grid scenarios. The user selects exactly one CIF model and exactly one scenario.

Event-trace example:

```bash
python3 benchmarks/benchmark_engine_vs_pycrop.py \
  --cif examples/coffee_machine.cif \
  --events-csv examples/coffee_machine_events.csv \
  --runs 3
```

Data-driven example:

```bash
python3 benchmarks/benchmark_engine_vs_pycrop.py \
  --cif examples/Grid_semplified.cif \
  --input-csv examples/grid_weather_input_48h_repeat.csv \
  --hours 48 \
  --limit 5 \
  --runs 3
```

The generated package is not regenerated by this benchmark. It must already exist in:

```text
out/generated/<MODEL_NAME>/
```

If it is missing, run:

```bash
./scripts/run_pipeline.sh MODEL.cif
```

first.

By default, PyCrop is read from:

```text
._pycrop/PyCrop_restrict
```

A different root can still be supplied with `--pycrop-root` for controlled local experiments.

## Outputs

By default, results are written to:

```text
out/outputs/<MODEL_NAME>/benchmarks/engine_vs_pycrop/
  engine_vs_pycrop_benchmark.csv
  engine_vs_pycrop_benchmark.json
  engine_vs_pycrop_benchmark.md
```

The output contains one row for the generic runtime and one row for PyCrop hosting. Each row reports mean, median, min and max execution time across the selected number of runs.

## Interpretation

This benchmark is useful for answering a narrow question:

```text
How expensive is it to execute the same generated package directly in the generic runtime
versus hosting it through the PyCrop adapter bridge?
```

It is less useful for small event-only models such as CoffeeMachine, because process startup overhead dominates the result. It becomes more meaningful on larger data-driven models such as Grid/Grid_semplified, where engine construction, adapter overhead, binding propagation and step execution contribute more substantially to the runtime.

The benchmark should therefore be presented as a secondary performance indicator for the hosting strategy, not as a central correctness result.
